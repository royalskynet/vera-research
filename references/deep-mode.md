# 深度編排：工作包（WP）→ 工作稿 → 綜合主報告

適用：使用者要求「深度／詳盡／完整」、矩陣超過 24 格、或題目跨多法域／多子題。疊加在 competitor／vendor-dd／academic 任一模式上；三輪流程、預算、深度門檻與禁詞全部照舊，本檔只規定**編排**。借鏡：evidence-research-report 深度模式（已併入，原拷貝不再保留）（問題清單＋完成條件、來源與主張台帳、最強反論）與 2026-09 方案 2.0 調研計畫（工作包分工、已覆蓋事實清單、定稿門檻清單）。

> **執行者能力（派 deep 時）**：`deep-run` 跑的是 DeepSeek，它**沒有** Agent／WebFetch／WebSearch／MCP 這些封裝工具，但**可透過 Bash 調用底層網路 CLI**——exa 搜尋、`curl r.jina.ai/URL`（Jina Reader）、`gh search`、`agent-reach`／`mcporter call` 等。因此 deep 不是只能讀寫檔，遇到指定任務裡沒給、但可自行補證的缺口（主管機關名冊、第三方佐證），**應先試著用 Bash 自己抓**，不要預設自己無能、把補證責任全丟回主 session。

## 0. 起點資產盤點（不重做既有工作）

1. Read 使用者提供的前版報告、方案、wiki 摘要。
2. 建 `<工作目錄>/wp/covered-facts.md`：事實｜來源 URL｜資料日期｜可直接引用？。
3. 後續各 WP 命中已覆蓋項只做時效複核（來源 >6 個月才重抓），否則直接引用。

## 1. 拆工作包

一個題目拆 3–7 個工作包，每包一行：

| WP | 目標（一句話） | 必答問題（3–8 題） | 對象／維度格 | 來源類型（S1–S5 各要哪些） | 交付 |
|---|---|---|---|---|---|
| WP-1 | … | … | 平台×維度 或 主體×D | … | `wp/wp-1.md` |

規則：
- 每個 WP 對應覆蓋矩陣的一組格；`budget.py init --mode <m> --platforms … --dims …` 一次建全矩陣，牆鐘依 `--minutes` 拉長（深度預設 240）。
- WP 之間互不依賴的可並行（可各派一個 `Agent` 子代理跑第一輪，子代理 prompt 自含該 WP 的問題、格、預算與工作稿路徑；最多 5 個，同一則回覆一次發出）。
- 監管基線類 WP（法定義務、名冊對照）先做，其他 WP 引用其結論。

## 2. 工作稿（不進報告）

每個 WP 產一份 `wp/wp-N.md`：
- 逐題回答（每題：結論一句＋證據 [N]＋來源等級＋資料日期）；
- 該 WP 的對比表儲存格草稿；
- 未答問題與原因（供第二輪缺口清單）；
- 來源台帳：序號｜等級｜日期｜支持哪些主張｜限制｜URL。

工作稿的引用序號在綜合時統一重編。工作稿與台帳是工作過程，不交付、不進報告。

## 3. 綜合主報告

- 依模式的報告格式（八章）由工作稿**融合**寫成：每個 WP 的結論回流到對比表、對應平台／維度段落、差距分析與建議結論；**不得**把工作稿當章節貼進去。
- 跨 WP 交叉：一個 WP 的發現改變另一個 WP 的判斷時（例：監管基線改變某平台的合規評述），回頭改寫。
- 第二輪缺口清單從各工作稿的「未答問題」彙總，仍受缺口上限；第三輪反方對主報告做。
- 對核心結論寫出最強反論（第三輪證據包之外，主 session 自己先寫一次）；反論成立就降低確定性或加前提。

## 4. 定稿門檻（全部滿足才交付）

- [ ] 每個 WP 的必答問題都有「已答＋[N]」或「本次已查阅的公开来源未能确认」。
- [ ] 主報告來源總數與正文字數達 `evidence-standards.md` 門檻（`check_report.sh <報告> --mode <m>` PASS）。
- [ ] 逐項語意核對完成（`validate_report.py --check-list` 全部逐行看過）；URL 存活。
- [ ] 建議結論有明確傾向，無空話結語。
- [ ] 報告正文簡體中文；無工作階段標記、無禁詞。
- [ ] 工作稿、台帳、已覆蓋事實清單、缺口清單、第三輪證據包都留在工作目錄，未進報告。
